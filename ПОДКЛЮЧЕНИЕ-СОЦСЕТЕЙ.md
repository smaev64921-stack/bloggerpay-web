# Подключение TikTok и YouTube

Чтобы блогер мог подтвердить, что канал действительно его, площадка должна
сама сообщить нам, чей это аккаунт. Для этого нужны ключи — их выдают
бесплатно в кабинете разработчика. Регистрация делается один раз и только
вами лично: это ваша учётная запись и ваше приложение.

**Код уже готов и проверен** (23 автоматические проверки, `server/test-verify.mjs`).
От вас — вписать два ключа в `server/.env` и перезапустить сервер. Больше
ничего менять не нужно.

Пока ключей нет, приложение не врёт: кнопка «Подтвердить» честно говорит,
что проверка ещё не настроена, и ничего не ломается.

---

## Порядок важен: сначала домен, потом регистрация

При создании приложения обе площадки **сразу требуют адрес возврата** — тот,
куда вас вернёт после входа. Это адрес вашего сервера, и он должен уже
существовать по `https`. Если зарегистрировать приложение раньше, придётся
возвращаться и переделывать.

Правильный порядок:

1. **Поднять сервер на VPS с HTTPS-доменом** — раздел «3½. Боевой запуск»
   в `ВЫКЛАДКА.md`. Нужен домен вида `kassa.вашдомен.ru`.
2. Прописать этот адрес в `server/.env` → `PUBLIC_URL=`.
3. **Выложить приложение** (там же в `ВЫКЛАДКА.md`) — заодно станет доступна
   страница политики конфиденциальности, её спросит Google.
4. И только теперь — регистрация приложений по инструкции ниже.

## Чем заменить «ваш адрес»

Везде ниже `https://kassa.вашдомен.ru` — это адрес вашего сервера-кассы
(то же значение, что стоит в `PUBLIC_URL` в `server/.env`).

**Самое важное правило:** адрес возврата (Redirect URI) должен совпадать
с тем, что ждёт сервер, **побуквенно**. Лишний слеш в конце, `http` вместо
`https` или другой поддомен — и площадка откажет со словами «redirect_uri
mismatch». Копируйте строки отсюда целиком.

## TikTok

1. Откройте **developers.tiktok.com**, войдите своим TikTok-аккаунтом.
2. **Manage apps → Create an app.** Название — `BloggerPay`.
3. В приложении добавьте продукт **Login Kit**.
4. В **Redirect URI** вставьте ровно эту строку:

```
https://kassa.вашдомен.ru/api/verify/callback/tiktok
```

5. В доступах (**Scopes**) отметьте три:

```
user.info.basic
user.info.profile
user.info.stats
```

6. Скопируйте **Client key** и **Client secret** в `server/.env`:

```
TT_CLIENT_KEY=сюда client key
TT_CLIENT_SECRET=сюда client secret
```

7. Перезапустите сервер.

**Про проверку приложения (App review).** TikTok открывает доступ к данным
пользователей после ревью — это обычная процедура, как у Google. Пока ревью
не пройдено, вход работает только для аккаунтов, добавленных в приложение
как тестовые (в разделе с участниками). На ревью у вас спросят, зачем нужны
доступы — отвечайте по делу: «блогер подтверждает владение своим каналом,
мы показываем рекламодателю имя канала и число подписчиков; ничего не
публикуем от его имени и данные третьим лицам не передаём».

## YouTube

1. Откройте **console.cloud.google.com**, создайте проект (название любое).
2. **APIs & Services → Library** → включите **YouTube Data API v3**.
3. **APIs & Services → OAuth consent screen** → тип **External**, заполните
   название приложения, почту поддержки и вашу почту.
4. **Credentials → Create credentials → OAuth client ID**, тип
   **Web application**.
5. В **Authorized redirect URIs** вставьте ровно эту строку:

```
https://kassa.вашдомен.ru/api/verify/callback/youtube
```

6. Скопируйте **Client ID** и **Client secret** в `server/.env`:

```
YT_CLIENT_ID=сюда client id
YT_CLIENT_SECRET=сюда client secret
```

7. Перезапустите сервер.

Доступ запрашивается только на чтение (`youtube.readonly`) — приложение
видит имя канала и число подписчиков и ничего не может изменить. Пока
приложение в статусе Testing, войти смогут только почты, добавленные в
списке тестовых пользователей; для всех — нужна публикация приложения.

## Что спросят на проверке — готовые ответы

Обе площадки проверяют приложение вручную и задают одни и те же вопросы.
Отвечайте коротко и по делу — ниже готовые формулировки, они соответствуют
тому, что сервис действительно делает.

**Название приложения:** `BloggerPay`

**Чем занимается приложение:**

> Биржа рекламы у блогеров. Рекламодатель находит блогера, деньги
> замораживаются на счёте сделки и переводятся исполнителю после
> выполнения работы. Блогеры подтверждают владение своими каналами,
> чтобы рекламодатель видел настоящие цифры, а не заявленные на словах.

**Зачем нужны запрошенные доступы:**

> Только чтобы подтвердить, что канал принадлежит человеку, который его
> указал. Мы получаем и показываем в профиле название канала и число
> подписчиков. Мы ничего не публикуем от имени пользователя, не читаем
> личные сообщения и не передаём эти данные третьим лицам.

**Что вы делаете с полученными данными:**

> Сохраняем идентификатор канала, название, ссылку и число подписчиков.
> Токен доступа не сохраняем — он используется однократно в момент
> проверки. Данные видны только самому пользователю и рекламодателям в
> его карточке.

**Ссылка на политику конфиденциальности** (её спрашивают обязательно):

```
https://адрес-вашего-сайта/privacy.html
```

Страница уже готова — файл `privacy.html` лежит рядом с приложением и
уезжает на хостинг вместе с ним. **Перед публикацией откройте её и
заполните два места**, помеченные синим: кто оператор данных (ИП или ООО с
ИНН) и адрес почты для обращений. Без этого проверку не пройти.

**Демонстрация работы.** Часто просят видео или скриншоты, где видно, как
пользователь нажимает «Подтвердить», входит на площадке и получает отметку
в профиле. Снимите экран телефона на этом пути — минуты достаточно.

## Как проверить, что заработало

1. В приложении: **Профиль → Редактировать → Площадки → Подтвердить**.
2. Откроется окно площадки, вы входите и разрешаете доступ.
3. Страница возврата покажет **шестизначный код** и название вашего канала.
4. Возвращаетесь в приложение — оно само предложит ввести этот код.
5. Ввели — кнопка становится «Подтверждён», в карточке блогера появляется
   отметка.

**Зачем код, а не просто «готово».** Без него работала бы простая подмена:
злоумышленник берёт свою ссылку авторизации, присылает её блогеру
(«подтвердите канал, чтобы получить заказ»), тот входит в свой аккаунт — и
его канал записывается на злоумышленника, а настоящий владелец навсегда
получает «канал уже привязан». Код видит только тот, кто действительно
вошёл на площадке, поэтому подсунутая ссылка бесполезна.

Если что-то пошло не так, страница возврата объяснит причину человеческим
языком («ссылка не найдена», «слишком долго», «канал уже привязан»).

Проверить контур можно и до получения ключей:

```bash
node server/test-verify.mjs
```

## Если канал привязали не туда

Канал продали, аккаунт потеряли, подтвердили не с того профиля — отвязать
может оператор своим ключом:

```bash
curl -X POST https://kassa.вашдомен.ru/api/admin/verify/unlink \
  -H "X-Admin-Key: ВАШ_КЛЮЧ" -H "Content-Type: application/json" \
  -d '{"platform":"tiktok","externalId":"идентификатор_канала"}'
```

Идентификатор виден в базе (таблица `channels`) — после отвязки канал
сможет подтвердить любой аккаунт.

## Что уже сделано за вас (менять не нужно)

- Ссылка авторизации собирается по правилам обеих площадок (у TikTok ключ
  уходит как `client_key`, у Google — как `client_id`; доступы и адрес
  возврата подставляются сами).
- Метка проверки — случайная, одноразовая и живёт 15 минут; канал
  привязывается только по коду, введённому в приложении (см. выше).
- Код можно ввести не больше пяти раз — потом проверку надо начать заново.
- Один канал — один аккаунт: второй человек тот же канал не подтвердит.
- Токен доступа используется один раз и не сохраняется — при утечке базы
  им нельзя воспользоваться.
- Внутри Телеграма ссылка открывается через сам Телеграм, иначе окно бы
  не открылось.
